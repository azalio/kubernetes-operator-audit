# Chapter 3 — Designing an Operator – CRD, API, and Target Reconciliation
Source: PDF 66–88; printed 45–67. Entire chapter read.

## Essence
Begin with an operational use case, define the public configuration and observation contract, then design convergence over relevant current resources. Watch notifications initiate examination; they are not a durable history of what must be done. API versions, storage representations, and diagnostic interfaces require intentional design before implementation.

## Audit checks
Book-derived principles, expressed as original audit procedures.
## B03-01 — Structural API contract
(pp. 49–54). Applies: CRD APIs. Evidence: generated and installed schemas, types/markers, sample CRs, validation tests. Fail: missing structural validation, invalid identity/scope, ambiguous units, or conflating absent and explicit-zero inputs changes meaning. Remedy: align types/schema/defaulting, validate input domains, and model optionality intentionally. Exactly one version must be storage-enabled.
## B03-02 — Level-based convergence
(pp. 57–60). Applies: all reconcilers. Evidence: reads of requested CR and relevant dependents, restart/repeated-reconcile/drift tests. Fail: behavior requires observing a particular previous event, or reconstructing state after restart cannot reach the target. Remedy: derive actions from persisted desired and observed state. Relevant state does not mean listing the entire cluster.
## B03-03 — Stable fixed point
(pp. 59–60). Applies: all resource writers. Evidence: compare/patch/update paths and no-change reconciliation traces. Fail: already-correct resources are rewritten indefinitely or updates self-trigger hot loops. Remedy: compare owned semantic fields and make repeated reconciliation a no-op. Explicit idempotency testing is the audit operationalization of the book's unnecessary-update warning.
## B03-04 — Concurrent change awareness
(p. 49). Applies: updates to existing objects. Evidence: resource-version handling and conflicting-writer tests. Fail: stale updates lose another actor's changes or conflicts cannot recover. Remedy: use concurrency-aware writes and retry from fresh state. Detailed retry mechanics are supplementation, not provided here.
## B03-05 — Version transition design
(pp. 60–62). Applies: multiple API/operand/operator versions. Evidence: served/storage declarations, compatibility and migration plan, upgrade/downgrade tests. Fail: removing an API strands stored objects or assumes changing storage flags rewrites existing data. Remedy: stage coexistence, conversion and verified storage migration before retirement; explicitly reject unsupported downgrade paths.
## B03-06 — Truthful conditions
(pp. 50, 63–64). Applies: status-bearing APIs. Evidence: status subresource, condition definitions, degraded and recovering-state samples. Fail: status expresses intended rather than observed health, changes meaning across releases, or stays healthy after a failure. Remedy: publish stable current-state conditions with diagnostic reasons; distinguish operator and operand readiness.
## B03-07 — Complementary diagnostics
(pp. 62–66). Applies: all operators. Evidence: error returns/backoff, logs, status and Kubernetes event recorder paths. Fail: persistent failures are silent or only discoverable in transient Pod logs. Remedy: combine actionable current status with bounded retries and useful events/logs; avoid treating Events as durable state.

## Traps and extrapolation boundaries
- The sample's singleton `instance` and claim that most operators should have one CR are not general requirements. Resource-per-tenant/instance operators are valid.
- Text repeatedly calls CR instances 'CRDs'. Distinguish schema installation failure from an individual CR's normal deletion; do not turn NotFound after deletion into an eternal error/recreation loop.
- `resourceVersion` is opaque, not an integer to compute; server-managed metadata should not be manually incremented. The sample CR's bare `v1alpha1` and example CRD naming need validation, not copying.
- Force-redeploy must be modeled as persisted desired rollout identity with bounded effects, not 'any notification means restart'. This safety constraint is audit extrapolation.
- Status helpers, fields, storage migration APIs, and predicted future automation are version-specific; verify against target dependencies. Conditions support Unknown and are not merely booleans. Readiness cannot be proven solely by controller startup.
