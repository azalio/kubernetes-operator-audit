# Chapter 3 — API, CRD and reconciliation design

## Essence
Begin with an operational use case, define the public configuration and observation contract, then design convergence over relevant current resources. Watch notifications initiate examination; they are not a durable history of what must be done. API versions, storage representations, and diagnostic interfaces require intentional design before implementation.

## Audit checks

## B03-01 — Structural API contract
Applies: CRD APIs. Evidence: generated and installed schemas, types/markers, sample CRs, validation tests. Fail: missing structural validation, invalid identity/scope, ambiguous units, or conflating absent and explicit-zero inputs changes meaning. Remedy: align types/schema/defaulting, validate input domains, and model optionality intentionally. Exactly one version must be storage-enabled.
## B03-02 — Level-based convergence
Applies: all reconcilers. Evidence: reads of requested CR and relevant dependents, restart/repeated-reconcile/drift tests. Fail: behavior requires observing a particular previous event, or reconstructing state after restart cannot reach the target. Remedy: derive actions from persisted desired and observed state. Relevant state does not mean listing the entire cluster.
## B03-03 — Stable fixed point
Applies: all resource writers. Evidence: compare/patch/update paths and no-change reconciliation traces. Fail: already-correct resources are rewritten indefinitely or updates self-trigger hot loops. Remedy: compare owned semantic fields and make repeated reconciliation a no-op.
## B03-04 — Concurrent change awareness
Applies: updates to existing objects. Evidence: resource-version handling and conflicting-writer tests. Fail: stale updates lose another actor's changes or conflicts cannot recover. Remedy: use concurrency-aware writes and retry from fresh state.
## B03-05 — Version transition design
Applies: multiple API/operand/operator versions. Evidence: served/storage declarations, compatibility and migration plan, upgrade/downgrade tests. Fail: removing an API strands stored objects or assumes changing storage flags rewrites existing data. Remedy: stage coexistence, conversion and verified storage migration before retirement; explicitly reject unsupported downgrade paths.
## B03-06 — Truthful conditions
Applies: status-bearing APIs. Evidence: status subresource, condition definitions, degraded and recovering-state samples. Fail: status expresses intended rather than observed health, changes meaning across releases, or stays healthy after a failure. Remedy: publish stable current-state conditions with diagnostic reasons; distinguish operator and operand readiness.
## B03-07 — Complementary diagnostics
Applies: all operators. Evidence: error returns/backoff, logs, status and Kubernetes event recorder paths. Fail: persistent failures are silent or only discoverable in transient Pod logs. Remedy: combine actionable current status with bounded retries and useful events/logs; avoid treating Events as durable state.

## Applicability and cautions
- Resource-per-tenant and resource-per-instance operators are valid; do not impose a singleton CR or hardcoded name.
- Distinguish CRD schema installation from individual CR lifecycle; NotFound after CR deletion must not cause an endless retry or recreation loop.
- Treat resourceVersion as opaque and server-managed. Validate API group/version and CRD naming against the installed schema.
- Model forced redeployment as persisted desired rollout identity with bounded effects, not as a restart on every notification.
- Verify status helpers, fields and migration APIs against target dependencies. Conditions support Unknown; controller startup alone does not prove operand readiness.
