# Chapter 1 — Operational responsibility and capabilities

## Essence
Operators encode workload-specific operational knowledge in controllers that compare intended configuration with actual conditions. The operand, operator, API contract, distribution tooling, and capability claims are distinct audit subjects. SDK, OLM, and OperatorHub serve different lifecycle stages; none alone proves safe automation. The capability model is a way to scope promised behavior, not a certification.

## Audit checks

## B01-01 — Operational responsibility
Applies: all operators. Evidence: architecture, supported operands, CR/API examples, operational runbooks. Fail: no clear mapping from automated tasks to managed resources, or important manual dependencies are hidden. Remedy: define ownership, configuration surface, and boundaries of automation.
## B01-02 — Desired-state control
Applies: all controllers. Evidence: reconciliation path and tests changing desired configuration or actual workload state. Fail: installation succeeds but subsequent drift cannot converge. Remedy: base correction on current versus desired state, not an assumed untouched installation.
## B01-03 — Capability claims
Applies: published feature/maturity claims. Evidence: demonstrations/tests for install, upgrades, lifecycle, insights, or autonomous actions actually advertised. Fail: metadata asserts capabilities absent from implementation. Remedy: implement and verify promised behavior or narrow claims. Do not require every level or every lifecycle feature.
## B01-04 — Operator/operand lifecycle separation
Applies: upgrade-capable products. Evidence: compatibility matrix and transitions across existing operand versions and operator versions. Fail: an operator update silently assumes a new/empty operand or unsupported rollback. Remedy: define supported transitions and explicit incompatibility handling.
## B01-05 — Operational visibility
Applies: all operators to the extent promised. Evidence: status/error reporting; metrics and alerts for deeper-insight claims. Fail: workload failure is indistinguishable from normal operation. Remedy: expose actionable operator and operand state; test degraded paths.
## B01-06 — Packaging is a scoped integration
Applies: chosen install/distribution mechanisms; OLM-specific evidence only for OLM users. Evidence: deploy manifests, dependencies, support contacts, optional bundle/CSV. Fail: advertised installation path lacks dependencies or accurate metadata. Remedy: validate that path; mark unrelated OLM/catalog checks not applicable rather than requiring adoption.

## Applicability and cautions
- SDK, OLM and OperatorHub are optional integrations; their absence does not exclude an implementation from operator review.
- Judge executable behavior and supported contracts rather than implementation language.
- CRDs need not originate in Go or a particular scaffold.
- Assign idempotency, conflict safety, credential handling and condition semantics to their owning chapter passes.
