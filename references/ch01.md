# Chapter 1 — Introducing the Operator Framework
Source: Michael Dame (2022), PDF 24–44, printed 3–23. Entire chapter read, including opener and final summary.

## Essence
Operators encode workload-specific operational knowledge in controllers that compare intended configuration with actual conditions. The operand, operator, API contract, distribution tooling, and capability claims are distinct audit subjects. SDK, OLM, and OperatorHub serve different lifecycle stages; none alone proves safe automation. The capability model is a way to scope promised behavior, not a certification.

## Audit checks
All checks below are book-derived principles translated into audit procedures; evidence/failure/remediation wording is audit synthesis.
## B01-01 — Operational responsibility
(pp. 4–8, 19–22). Applies: all operators. Evidence: architecture, supported operands, CR/API examples, operational runbooks. Fail: no clear mapping from automated tasks to managed resources, or important manual dependencies are hidden. Remedy: define ownership, configuration surface, and boundaries of automation.
## B01-02 — Desired-state control
(pp. 6–8). Applies: all controllers. Evidence: reconciliation path and tests changing desired configuration or actual workload state. Fail: installation succeeds but subsequent drift cannot converge. Remedy: base correction on current versus desired state, not an assumed untouched installation.
## B01-03 — Capability claims
(pp. 14–18). Applies: published feature/maturity claims. Evidence: demonstrations/tests for install, upgrades, lifecycle, insights, or autonomous actions actually advertised. Fail: metadata asserts capabilities absent from implementation. Remedy: implement and verify promised behavior or narrow claims. Do not require every level or every lifecycle feature.
## B01-04 — Operator/operand lifecycle separation
(pp. 15–17). Applies: upgrade-capable products. Evidence: compatibility matrix and transitions across existing operand versions and operator versions. Fail: an operator update silently assumes a new/empty operand or unsupported rollback. Remedy: define supported transitions and explicit incompatibility handling.
## B01-05 — Operational visibility
(pp. 17–18, 22). Applies: all operators to the extent promised. Evidence: status/error reporting; metrics and alerts for deeper-insight claims. Fail: workload failure is indistinguishable from normal operation. Remedy: expose actionable operator and operand state; test degraded paths.
## B01-06 — Packaging is a scoped integration
(pp. 8–14). Applies: chosen install/distribution mechanisms; OLM-specific evidence only for OLM users. Evidence: deploy manifests, dependencies, support contacts, optional bundle/CSV. Fail: advertised installation path lacks dependencies or accurate metadata. Remedy: validate that path; mark unrelated OLM/catalog checks not applicable rather than requiring adoption.

## Traps and extrapolation boundaries
- The text explicitly permits non-SDK operators and deployment without OLM. Its later suggestion that framework pillars distinguish all operators must not become a universal eligibility test.
- Toolkit/language capability limits are historical simplifications; pp. 19 also overgeneralizes Ansible limits relative to the earlier model. Judge executable behavior, not implementation language.
- CRDs need not originate in Go; generated Go scaffolding is this book's development path.
- Strong idempotency, conflict safety, secret-handling and precise modern condition conventions require later chapters or modern supplements; this chapter supplies their motivation, not complete specifications.
