# Chapter 11 — Stateful and core-operator safety

## Essence
Core-component automation can affect authorization, scheduling, storage and cluster recovery. Audit supported configuration changes, data preservation, recovery status and assumptions about available dependencies. Missing workloads alone must not authorize automatic reconstruction of a database.

No recovery commands are supplied or executed.

## B11-01 — Identify critical dependencies and recovery authority
Applies: operators controlling authorization, scheduling, storage or other critical infrastructure.
Evidence: dependency graph, deployment location, blast-radius analysis, escalation and recovery ownership.
Fail: the operator is treated as an ordinary workload despite its ability to disable the platform, or its own recovery requires an unavailable operand/API with no alternative path.
Remedy: document failure domains and a supported break-glass path. Verify bootstrap and recovery when the API or a managed dependency is unavailable.

## B11-02 — Safe and bounded configuration changes
Applies: powerful configuration or authorization controllers.
Evidence: allowed profiles/validation, generated RBAC or scheduling configuration, rollout sequence, invalid-input tests.
Fail: accepted input can trivially remove required access or render critical components unusable, with no guard or recoverable rollout.
Remedy: constrain unsupported combinations, provide tested presets where useful, and document consequences of low-level overrides. Evaluate the actual API contract rather than requiring a particular preset or Boolean field shape.

## B11-03 — Backup success includes recoverability
Applies: promised backup/restore features and critical stateful operands.
Evidence: backup and restore APIs/controllers, destination and credential references, operation status, a verified restore exercise against disposable data.
Fail: creating a backup request is called successful protection, stored backup is inaccessible/corrupt, or restoration silently targets the wrong cluster.
Remedy: validate artifacts and destination identity, report progress/errors, and test documented restore procedures. Verify integrity, retention, credential access and explicit recovery objectives.

## B11-04 — Ambiguous failure does not authorize data destruction
Applies: automatic recovery or stateful reconciliation.
Evidence: persisted initialization/recovery state, membership and health observations, restart/recovery branches, partition and lost-Pod simulations.
Fail: empty Pod lists, temporary API failures or operator restart are treated as proof that data should be reinitialized or restored over existing data.
Remedy: reconstruct durable state, discriminate initialization from failure, and stop/escalate when safe recovery cannot be established. An empty Pod list alone must not trigger restoration over existing data.

## B11-05 — Quorum and failure-domain protection
Applies: quorum-based replicated operands.
Evidence: membership/health logic, placement and disruption settings, scaling/replacement sequence, node-loss tests.
Fail: replica count substitutes for healthy voting membership, correlated placement removes quorum on one failure, or scaling disrupts too many members together.
Remedy: respect the operand's membership protocol and distribute replicas across appropriate failure domains; verify available capacity.

## B11-06 — Deletion and uninstall preserve intended data
Applies: stateful/critical operators and cleanup workflows.
Evidence: owner references, finalizers, uninstall scripts, CR/PVC/external-data retention policy and destructive-action tests.
Fail: deleting the operator unexpectedly removes live clusters/backups or cleanup cannot complete safely.
Remedy: separate removing management from deleting the managed data, document retention, and require explicit destructive intent. Test finalizer and PVC retention behavior against that policy.

## B11-07 — Upgrade compatibility and recovery are operand-specific
Applies: critical component upgrades.
Evidence: Kubernetes/operator/operand compatibility matrix, supported upgrade edges, rolling health gates, pre-upgrade backups and tested recovery procedure.
Fail: unsupported version jumps proceed, multiple members become unavailable without safety checks, or reverting an image is assumed to undo data-format changes.
Remedy: enforce the operand's supported path, validate each stage and halt safely on degradation; define realistic restoration/rollback limits. Verify allowed version jumps against the actual operand and platform support policy.

## Applicability and cautions
Use supported platform procedures for critical-component recovery. Application etcd clusters and the hosting control-plane datastore have different ownership and bootstrap constraints. CRD existence alone does not prove prior initialization of an individual cluster. Automation does not by itself validate backups or guarantee zero downtime. Verify distribution-specific scheduler behavior. Real etcd recovery requires preserved evidence, authorized maintenance scope and verified backups; audit guidance is not an executable recovery procedure.
