# Chapter 2 — Understanding How Operators Interact with Kubernetes
Source: PDF 46–62; printed 25–41. Entire chapter read.

## Essence
An operator's resource model and human interface must be designed together. Native workload controllers supply useful rollout and replica behavior; custom APIs should expose a deliberate, supportable subset rather than duplicate all Kubernetes controls. Namespace reach, access permissions, user roles, emergency recovery, maintainership, and deprecation are design decisions, not packaging afterthoughts.

## Audit checks
Book-derived principles; audit procedures are original synthesis.
## B02-01 — Delegate native workload mechanics
(pp. 27–28, 37). Applies: operators managing workloads. Evidence: resource graph and rationale for Deployment, raw Pod, or other workload primitive. Fail: unnecessary replacement of native replica/rollout logic creates unhandled failure paths. Remedy: use appropriate native primitives or document and test the specialized behavior. Deployment is not mandatory for every operand.
## B02-02 — Align authorization with actual scope
(pp. 29–31). Applies: all Kubernetes API clients. Evidence: ServiceAccounts, Role/ClusterRole rules and bindings, watched namespaces, CR scope, API calls. Fail: missing permissions block reconciliation or broad privileges have no task-based justification. Remedy: reconcile required resources/verbs and binding scope with intended reach. Least-privilege review is an audit extrapolation from the access-policy discussion; sample wildcards are not a recommendation.
## B02-03 — Usable configuration contract
(pp. 28–29, 32–35). Applies: exposed APIs and frontends. Evidence: CR examples, validation, user personas and integration clients. Fail: normal operations require undocumented direct editing of managed resources, or ordinary users can request administrator-only actions without controls. Remedy: define supported operations and authorization at the correct interface.
## B02-04 — Emergency intervention
(pp. 32–33). Applies: workloads needing operator-assisted or manual recovery. Evidence: recovery runbook and tested intervention procedure. Fail: restrictive abstraction prevents necessary repair, or reconciliation immediately undoes repairs without a supported process. Remedy: document controlled emergency access and return-to-management procedure. Pause/override mechanisms are possible implementations, not a book mandate.
## B02-05 — Supported feature scope and ownership
(pp. 36–39). Applies: all projects. Evidence: maintainers, review responsibility, user demand and feature support commitments. Fail: unsupported speculative features or absent reviewers leave essential operational behavior unmaintained. Remedy: narrow scope, appoint knowledgeable owners, and validate required features against actual use cases.
## B02-06 — Predictable deprecation
(pp. 38–40). Applies: removed/changed APIs or behavior. Evidence: policy, release notes, notices and migration instructions. Fail: supported workflows disappear without reasonable notice or alternatives. Remedy: plan staged retirement and publish migration paths; chapter 8 supplies deeper API-transition guidance.

## Traps and extrapolation boundaries
The book conflates controller watch scope, resource scope, and authorization in places. Audit all three independently: a namespaced CR can be watched cluster-wide; cross-namespace access need not imply unrestricted cluster-admin. Namespace partitioning is not by itself complete security isolation. Deployment ownership is not automatic ownership of every operator resource. Do not infer trust in all internal users from the chapter's illustrative persona descriptions.
