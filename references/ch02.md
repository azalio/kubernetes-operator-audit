# Chapter 2 — Kubernetes interaction, actors and scope

## Essence
An operator's resource model and human interface must be designed together. Native workload controllers supply useful rollout and replica behavior; custom APIs should expose a deliberate, supportable subset rather than duplicate all Kubernetes controls. Namespace reach, access permissions, user roles, emergency recovery, maintainership, and deprecation are design decisions, not packaging afterthoughts.

## Audit checks

## B02-01 — Delegate native workload mechanics
Applies: operators managing workloads. Evidence: resource graph and rationale for Deployment, raw Pod, or other workload primitive. Fail: unnecessary replacement of native replica/rollout logic creates unhandled failure paths. Remedy: use appropriate native primitives or document and test the specialized behavior. Deployment is not mandatory for every operand.
## B02-02 — Align authorization with actual scope
Applies: all Kubernetes API clients. Evidence: ServiceAccounts, Role/ClusterRole rules and bindings, watched namespaces, CR scope, API calls. Fail: missing permissions block reconciliation or broad privileges have no task-based justification. Remedy: reconcile required resources/verbs and binding scope with intended reach. Require a task-based justification for wildcard permissions.
## B02-03 — Usable configuration contract
Applies: exposed APIs and frontends. Evidence: CR examples, validation, user personas and integration clients. Fail: normal operations require undocumented direct editing of managed resources, or ordinary users can request administrator-only actions without controls. Remedy: define supported operations and authorization at the correct interface.
## B02-04 — Emergency intervention
Applies: workloads needing operator-assisted or manual recovery. Evidence: recovery runbook and tested intervention procedure. Fail: restrictive abstraction prevents necessary repair, or reconciliation immediately undoes repairs without a supported process. Remedy: document controlled emergency access and return-to-management procedure. Pause/override mechanisms are possible implementations, not universal requirements.
## B02-05 — Supported feature scope and ownership
Applies: all projects. Evidence: maintainers, review responsibility, user demand and feature support commitments. Fail: unsupported speculative features or absent reviewers leave essential operational behavior unmaintained. Remedy: narrow scope, appoint knowledgeable owners, and validate required features against actual use cases.
## B02-06 — Predictable deprecation
Applies: removed/changed APIs or behavior. Evidence: policy, release notes, notices and migration instructions. Fail: supported workflows disappear without reasonable notice or alternatives. Remedy: plan staged retirement and publish migration paths; chapter 8 supplies deeper API-transition guidance.

## Applicability and cautions
Audit controller watch scope, resource scope and authorization independently: a namespaced CR can be watched cluster-wide; cross-namespace access need not imply unrestricted cluster-admin. Namespace partitioning is not by itself complete security isolation. Deployment ownership is not automatic ownership of every operator resource. Internal users still require explicit trust and authorization boundaries.
