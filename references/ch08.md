# Chapter 8 — Preparing for Ongoing Maintenance of Your Operator
Source: PDF 206–242; printed 185–221. Entire chapter read in contiguous parts.

## Essence
Release evolution joins API compatibility, conversion deployment, persistent-storage migration and distribution metadata. Serving both API versions is useful only when conversions preserve meaning and installed clients remain functional. Upstream release/deprecation awareness and maintained dependency boundaries prevent late compatibility surprises; operators may choose their own documented support policies.

## Audit checks
Book-derived principles with original audit procedures.
## B08-01 — Compatible API evolution
(pp. 187–194, 209–213). Applies: CRD schema changes. Evidence: old/new schema diff, supported version declarations, old-client fixtures. Fail: fields disappear or change meaning within a promised stable API, or a supposedly additive field breaks old objects. Remedy: preserve existing contracts, stage incompatible changes in a new version, and test defaults/requiredness as well as types.
## B08-02 — Lossless conversion round trips
(pp. 194–198, 211–213). Applies: multiple served representations requiring conversion. Evidence: every conversion direction with complete spec/status/metadata, unset/zero/empty and multi-element fixtures. Fail: reads followed by old-client updates erase newer data, list truncation loses fields, or conversion panics. Remedy: preserve nonrepresentable data by a documented compatible mechanism or redesign the transition; test round trips and old-client edits. Do not excuse silent data loss because an API is alpha.
## B08-03 — Conversion service is deployable and available
(pp. 195–205). Applies: conversion webhooks. Evidence: CRD webhook configuration, service/endpoints, TLS trust/certificate provisioning, server registration and explicit-version API requests. Fail: conversion functions compile but the API server cannot call them, or protocol versions are wrong. Remedy: deploy and validate the full webhook path, dependency ordering, and failure recovery. Certificate-rotation/outage tests are audit extrapolation.
## B08-04 — Storage migration precedes retirement
(pp. 192–194, 205). Applies: storage-version changes. Evidence: storage flags, persisted-version inventory, migration execution/verification and rollback policy. Fail: merely flipping storage=true is treated as migrating existing objects, or old conversion support is removed prematurely. Remedy: migrate existing data with supported tooling, verify completion and retain required readers/converters until safe retirement.
## B08-05 — Release identity and upgrade path
(pp. 206–209). Applies: releases; CSV/channel specifics only for OLM. Evidence: runtime image, bundle version, API set, replaces/channel graph and upgrade tests from installed prior versions. Fail: clean installation is presented as upgrade validation, published artifact references disagree, or upgrade graph bypasses required transitions. Remedy: test real supported upgrade edges with pre-existing CRs/data and publish matching metadata.
## B08-06 — Explicit support and deprecation policy
(pp. 209–214). Applies: maintained public contracts. Evidence: notices, supported API/cluster/operand versions and migration guidance. Fail: removals violate commitments or users cannot determine support windows. Remedy: state policy and honor it; use upstream policy as a model, not an automatically binding timeline.
## B08-07 — Dependency and upstream-change maintenance
(pp. 214–221). Applies: Kubernetes-dependent projects. Evidence: pinned compatible component libraries, update cadence, deprecation tracking, tests on supported/new cluster versions, assigned owners. Fail: reliance on removed APIs or unmanaged dependency drift blocks supported clusters. Remedy: track relevant releases/KEPs, test upcoming changes, and prefer published component libraries over importing the Kubernetes monorepo. Community participation is useful, not a compliance requirement.

## Traps and extrapolation boundaries
The sample explicitly loses all but the first port in reverse conversion; later discussion acknowledges this and suggests preserving extra data. Treat it as a negative audit example. **conversionReviewVersions describes the webhook ConversionReview protocol, not CR API versions**: the instruction to add v1alpha1/v1alpha2 there is a critical error to reject. A default kubectl GET does not establish the actual storage encoding; discovery's preferred version and storage version are distinct. Hub version and storage version are conceptually distinct even when the sample uses the same one. A controller need not always consume the newest API if conversion and semantics are supported. cert-manager is one TLS provisioner, not mandatory. Historical cadence, support windows, generated layouts and commands require current authoritative verification. Adding required fields or changing defaults can make an 'addition' breaking.
