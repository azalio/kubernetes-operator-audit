# Chapter 8 — API evolution and maintenance

## Essence
Release evolution joins API compatibility, conversion deployment, persistent-storage migration and distribution metadata. Serving both API versions is useful only when conversions preserve meaning and installed clients remain functional. Upstream release/deprecation awareness and maintained dependency boundaries prevent late compatibility surprises; operators may choose their own documented support policies.

## Audit checks

## B08-01 — Compatible API evolution
Applies: CRD schema changes. Evidence: old/new schema diff, supported version declarations, old-client fixtures. Fail: fields disappear or change meaning within a promised stable API, or a supposedly additive field breaks old objects. Remedy: preserve existing contracts, stage incompatible changes in a new version, and test defaults/requiredness as well as types.
## B08-02 — Lossless conversion round trips
Applies: multiple served representations requiring conversion. Evidence: every conversion direction with complete spec/status/metadata, unset/zero/empty and multi-element fixtures. Fail: reads followed by old-client updates erase newer data, list truncation loses fields, or conversion panics. Remedy: preserve nonrepresentable data by a documented compatible mechanism or redesign the transition; test round trips and old-client edits. Do not excuse silent data loss because an API is alpha.
## B08-03 — Conversion service is deployable and available
Applies: conversion webhooks. Evidence: CRD webhook configuration, service/endpoints, TLS trust/certificate provisioning, server registration and explicit-version API requests. Fail: conversion functions compile but the API server cannot call them, or protocol versions are wrong. Remedy: deploy and validate the full webhook path, dependency ordering, and failure recovery.
## B08-04 — Storage migration precedes retirement
Applies: storage-version changes. Evidence: storage flags, persisted-version inventory, migration execution/verification and rollback policy. Fail: merely flipping storage=true is treated as migrating existing objects, or old conversion support is removed prematurely. Remedy: migrate existing data with supported tooling, verify completion and retain required readers/converters until safe retirement.
## B08-05 — Release identity and upgrade path
Applies: releases; CSV/channel specifics only for OLM. Evidence: runtime image, bundle version, API set, replaces/channel graph and upgrade tests from installed prior versions. Fail: clean installation is presented as upgrade validation, published artifact references disagree, or upgrade graph bypasses required transitions. Remedy: test real supported upgrade edges with pre-existing CRs/data and publish matching metadata.
## B08-06 — Explicit support and deprecation policy
Applies: maintained public contracts. Evidence: notices, supported API/cluster/operand versions and migration guidance. Fail: removals violate commitments or users cannot determine support windows. Remedy: state policy and honor it; use upstream policy as a model, not an automatically binding timeline.
## B08-07 — Dependency and upstream-change maintenance
Applies: Kubernetes-dependent projects. Evidence: pinned compatible component libraries, update cadence, deprecation tracking, tests on supported/new cluster versions, assigned owners. Fail: reliance on removed APIs or unmanaged dependency drift blocks supported clusters. Remedy: track relevant releases/KEPs, test upcoming changes, and prefer published component libraries over importing the Kubernetes monorepo. Community participation is useful, not a compliance requirement.

## Applicability and cautions
Reverse conversion must preserve all permitted values, including multi-element lists. conversionReviewVersions describes the webhook ConversionReview protocol, not CR API versions. A default kubectl GET does not establish storage encoding: discovery's preferred version and storage version are distinct. Hub version and storage version are separate concepts even when configured identically. A controller may consume a supported older API when conversion preserves semantics. cert-manager is one TLS provisioner, not mandatory. Verify support windows, generated layouts and commands against current authoritative documentation. Adding required fields or changing defaults can break compatibility.
