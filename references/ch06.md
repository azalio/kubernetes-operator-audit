# Chapter 6 — Building and Deploying Your Operator
Source: PDF 150–174; printed 129–153. Entire chapter read.

## Essence
A local build, an image build, image availability, manifest application, controller readiness, operand convergence, and successful scraping are separate milestones. Disposable clusters enable iterative verification. Troubleshooting should descend through the actual build commands and runtime resource state rather than equate a successful wrapper command with a functioning operator.

## Audit checks
Book-derived principles, operationalized for audits.
## B06-01 — Release build includes all inputs
(pp. 131–136, 149–150). Applies: compiled/containerized releases. Evidence: build definitions, module locks, generated-code checks, actual image build output. Fail: local build succeeds while image build omits templates/packages, targets skip expected checks, or architecture is incompatible. Remedy: test the real release build with complete sources and target platform settings.
## B06-02 — Artifact identity reaches deployment
(pp. 136–140, 150–151). Applies: image deployments. Evidence: build/push references, rendered workload image, running image identity, pull events. Fail: default/sample image is deployed, stale tag masks changes, or cluster lacks registry access. Remedy: use consistent explicit references and verify the deployed artifact. Digest verification is audit extrapolation supporting the chapter's identity chain.
## B06-03 — End-to-end behavioral smoke test
(pp. 140–143). Applies: supported installation path. Evidence: CR creation, operand observation, supported configuration changes, zero/omitted-value handling and status. Fail: controller is Running but cannot reconcile, or status says success without expected workload changes. Remedy: test the public API through to actual operand behavior on a disposable supported cluster.
## B06-04 — Non-destructive iteration
(pp. 143–147). Applies: upgrade/redeploy workflows. Evidence: rendered diff, deploy/undeploy target definitions, CR/data retention tests. Fail: normal update instructions delete CRDs or stored resources unnecessarily. Remedy: prefer in-place declarative updates, reserve destructive cleanup for explicitly disposable environments, and disclose deletion scope. Safety/retention requirements are audit extrapolation from the chapter's optional undeploy step.
## B06-05 — Complete metrics delivery chain
(pp. 144–147, 152–153). Applies: advertised Prometheus integration. Evidence: installed monitor CRD, monitor selectors and namespace reach, Service endpoint, scrape target and actual query result. Fail: exported metric never reaches the backend or optional monitoring breaks otherwise valid installation. Remedy: declare dependencies and align discovery/endpoint configuration; verify a changing metric, not just monitor object creation.
## B06-06 — Diagnose partial installation
(pp. 148–153). Applies: deploy scripts and support procedures. Evidence: command failures plus per-resource state, Pod events/logs, missing API and pull failures. Fail: partial apply is declared complete or unrelated resources are repeatedly reinstalled without identifying the failure. Remedy: report which components work, find the underlying failed command/resource, and repair only the relevant dependency/configuration.

## Traps and extrapolation boundaries
OLM is not a universal production prerequisite; another tested lifecycle mechanism is valid. Public registries, Docker, kind and specific SDK Make targets are examples, not requirements. Do not fix private-registry pull failures by making images public; use appropriate credentials. Installing plain Prometheus does not install ServiceMonitor CRDs: those belong to the Prometheus Operator ecosystem. `kubectl get all` is not exhaustive. Historic Go/Kubernetes images and default scaffold security settings need modern review. Build/push/deploy command success cannot replace readiness and behavioral tests.
