# Chapter 7 — Installing and Running Operators with the Operator Lifecycle Manager
Source: PDF 178–204; printed 157–183. Entire chapter read.

## Essence
OLM consumes a distinct bundle artifact containing installation metadata, APIs, permissions and deployment definitions. Catalog distribution adds discoverability and support information but does not demonstrate runtime correctness. Packaging, installation scope and dependency declarations must agree with controller behavior. These integrations are optional and should be audited only where offered.

## Audit checks
Book-derived checks; evidence/failure/remediation are original audit synthesis. Mark OLM/catalog-specific checks N/A with rationale for other deployment models.
## B07-01 — OLM prerequisite health
(pp. 159–163). Applies: OLM-managed installation. Evidence: target OLM version, CRDs, controller/registry health and installation diagnostics. Fail: missing infrastructure is mistaken for an operator logic failure or unsupported versions are silently assumed. Remedy: declare supported integration versions and verify prerequisites without destructive repair of a shared cluster.
## B07-02 — Bundle/internal artifact consistency
(pp. 163–172). Applies: bundles. Evidence: bundle manifests, CSV deployment image, bundle metadata/image labels, build outputs and validation. Fail: wrong operator image/version, mismatched metadata, missing CRDs or an inaccessible bundle/runtime image. Remedy: generate from the intended release, validate both artifact references, and test the published bundle itself.
## B07-03 — Install modes reflect real isolation
(pp. 166–168, 172). Applies: advertised OLM namespace modes. Evidence: CSV installModes, OperatorGroup targets, RBAC and actual watch configuration. Fail: a supported mode cannot reconcile or observes/writes outside its promised scope. Remedy: enable only tested modes and align watch and permission configuration. Test design is extrapolation from mode declarations.
## B07-04 — Owned/required APIs and dependencies
(pp. 166–172). Applies: OLM dependency installation. Evidence: CSV CRD declarations, other bundled resources, required monitoring APIs, install states. Fail: conflicting ownership or undeclared required APIs stall installation. Remedy: accurately declare dependencies and separate optional features where supported; avoid requiring kube-prometheus universally.
## B07-05 — Actual installation acceptance
(pp. 172, 174–177). Applies: shipped bundles/catalog entries. Evidence: Subscription/InstallPlan/CSV states, deployed controller, documented sample CR and resulting operand. Fail: catalog registration or CSV creation alone is called a working install. Remedy: verify installation completion and run the published quick-start through operand convergence.
## B07-06 — Publication contract and maintainership
(pp. 165–168, 178–183). Applies: public catalog publication. Evidence: accurate capability/version metadata, valid examples, support links, reviewer ownership and current catalog validation. Fail: template placeholders, misleading capabilities or broken onboarding reach users. Remedy: validate and preview the exact submission, test examples, and maintain responsible contacts.
## B07-07 — Removal scope is explicit
(pp. 163, 173). Applies: uninstall/cleanup instructions. Evidence: command implementation and CR/CRD/data retention behavior. Fail: users assume removing OLM removes operators, or development cleanup deletes APIs/data unexpectedly. Remedy: distinguish OLM removal, operator removal and operand/data deletion; gate destructive actions and verify retention. Explicit authorization/retention testing is audit extrapolation.

## Traps and extrapolation boundaries
Do not execute the illustrative deletion of OperatorGroup CRDs or uninstall/reinstall OLM as routine production troubleshooting. `operator-sdk cleanup` example deletes a CRD; it is not a universally safe uninstall recipe. Bundle image is metadata, not the runnable operator binary image. Public OperatorHub publishing is not required, and catalog acceptance is not a security/correctness certification. Repository locations, submission automation, OLM internals, SDK commands and sample version defaults are historical; inspect current target tooling before use. This chapter introduces lifecycle packaging, not comprehensive proof of safe upgrades or automatic downgrade support.
