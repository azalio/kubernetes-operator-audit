# Chapter 5 — Developing an Operator – Advanced Functionality
Source: PDF 122–148; printed 101–127. Entire chapter read in contiguous parts.

## Essence
Conditions, metrics, leadership coordination and health endpoints make automation diagnosable and more resilient. Implementing these interfaces is not enough: their reported state must mean what consumers assume, and optional integration with OLM must remain distinct from native CR status. More features are justified by operational needs, not a requirement to reach the highest capability label.

## Audit checks
Book-derived principles; detailed verification and remedies are audit synthesis.
## B05-01 — Reliable condition publication
(pp. 103–111). Applies: CR status writers. Evidence: condition schema/helpers, all failure and recovery branches, status subresource permissions, status-write failure tests. Fail: stale degradation after recovery, missing reason/message, swallowed primary error, or every pass unnecessarily changes status. Remedy: update semantically changed conditions, retain useful original errors and handle status-write failures separately. Verify actual operand health separately from successful API writes.
## B05-02 — Scoped upgrade gating
(pp. 111–114). Applies: OLM installations with critical non-interruptible operations. Evidence: installed OperatorCondition API, Upgradeable transitions, blocked-upgrade/resume and override runbook tests. Fail: an unsafe phase is advertised upgradeable, a completed phase blocks forever, or non-OLM installations require unavailable OLM objects. Remedy: publish correct gates for chosen integration and make override consequences explicit. Not applicable outside that deployment model.
## B05-03 — Useful service metrics
(pp. 114–120). Applies: operational monitoring, especially insight claims. Evidence: scrape output, metric registration and update locations, rate/error/duration series. Fail: endpoint exists but counters never update, failures are excluded unintentionally, or names/units hide semantics. Remedy: use built-in controller metrics and add workload-specific measures with clear prefixes and units; exercise successful and failed work.
## B05-04 — Leadership configuration actually takes effect
(pp. 121–125). Applies: multiple potential writers or HA requirements. Evidence: deployed flags, replica counts, lock identity/namespace, permissions, startup and failover traces. Fail: replicas act simultaneously where exclusivity is required, lock collisions couple unrelated operators, or successors cannot take over. Remedy: select and configure a supported coordination strategy and test loss of the active instance. Equivalent safe coordination is acceptable.
## B05-05 — Leadership failure assumptions
(pp. 122–124). Applies: leader-elected controllers and external side effects. Evidence: renewal settings, API outage/partition tests and documented safety limits. Fail: claims of absolute single-writer guarantees rely solely on lease election or old leader work continues unsafely. Remedy: validate deadlines and shutdown/cancellation; where needed add application-level fencing/idempotency. Fencing is an explicit audit extrapolation, not a recipe supplied by the chapter.
## B05-06 — Meaningful liveness and readiness
(pp. 125–127). Applies: deployed health probes. Evidence: endpoint handlers and Pod probe definitions, startup/dependency/failure tests. Fail: readiness asserts service capability before required components initialize, probe is not wired to the right endpoint, or health semantics are undocumented. Remedy: define separate liveness and readiness contracts and implement bounded appropriate checks. Avoid restarting a healthy process merely for a transient downstream failure (audit extrapolation).

## Traps and extrapolation boundaries
Always-successful `healthz.Ping` is explicitly a minimal scaffold, not proof of operational readiness and not universally wrong for a deliberately basic liveness check. The sample's duplicated reconcile counter is teaching instrumentation, not a required metric. Updating an unfetched/empty CR status after Get failure may not work. Unconditional status updates can hot-loop. OLM API versions and write fields vary: validate the installed contract rather than copy the mixed v1/v2 examples. Leader-for-life and its ConfigMap lock example are historical options, not universal recommendations or an unconditional split-brain cure. The clock-skew worked narrative is not a safe tuning recipe. Operator failover alone does not establish operand lifecycle capability.
