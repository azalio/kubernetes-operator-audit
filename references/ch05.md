# Chapter 5 — Conditions, metrics, election and probes

## Essence
Conditions, metrics, leadership coordination and health endpoints make automation diagnosable and more resilient. Implementing these interfaces is not enough: their reported state must mean what consumers assume, and optional integration with OLM must remain distinct from native CR status. More features are justified by operational needs, not a requirement to reach the highest capability label.

## Audit checks

## B05-01 — Reliable condition publication
Applies: CR status writers. Evidence: condition schema/helpers, all failure and recovery branches, status subresource permissions, status-write failure tests. Fail: stale degradation after recovery, missing reason/message, swallowed primary error, or every pass unnecessarily changes status. Remedy: update semantically changed conditions, retain useful original errors and handle status-write failures separately. Verify actual operand health separately from successful API writes.
## B05-02 — Scoped upgrade gating
Applies: OLM installations with critical non-interruptible operations. Evidence: installed OperatorCondition API, Upgradeable transitions, blocked-upgrade/resume and override runbook tests. Fail: an unsafe phase is advertised upgradeable, a completed phase blocks forever, or non-OLM installations require unavailable OLM objects. Remedy: publish correct gates for chosen integration and make override consequences explicit. Not applicable outside that deployment model.
## B05-03 — Useful service metrics
Applies: operational monitoring, especially insight claims. Evidence: scrape output, metric registration and update locations, rate/error/duration series. Fail: endpoint exists but counters never update, failures are excluded unintentionally, or names/units hide semantics. Remedy: use built-in controller metrics and add workload-specific measures with clear prefixes and units; exercise successful and failed work.
## B05-04 — Leadership configuration actually takes effect
Applies: multiple potential writers or HA requirements. Evidence: deployed flags, replica counts, lock identity/namespace, permissions, startup and failover traces. Fail: replicas act simultaneously where exclusivity is required, lock collisions couple unrelated operators, or successors cannot take over. Remedy: select and configure a supported coordination strategy and test loss of the active instance. Equivalent safe coordination is acceptable.
## B05-05 — Leadership failure assumptions
Applies: leader-elected controllers and external side effects. Evidence: renewal settings, API outage/partition tests and documented safety limits. Fail: claims of absolute single-writer guarantees rely solely on lease election or old leader work continues unsafely. Remedy: validate deadlines and shutdown/cancellation; where needed add application-level fencing/idempotency.
## B05-06 — Meaningful liveness and readiness
Applies: deployed health probes. Evidence: endpoint handlers and Pod probe definitions, startup/dependency/failure tests. Fail: readiness asserts service capability before required components initialize, probe is not wired to the right endpoint, or health semantics are undocumented. Remedy: define separate liveness and readiness contracts and implement bounded appropriate checks. Avoid restarting a healthy process merely for a transient downstream failure.

## Applicability and cautions
A successful healthz.Ping does not prove operand readiness; it can be appropriate for a deliberately basic process liveness check. Metrics must represent meaningful events without accidental duplicate counting. Do not write an unfetched or empty CR status after Get failure, and avoid unconditional status writes that trigger hot loops. Verify OLM APIs and writable fields against the installed version. Check the coordination implementation's failure assumptions and timing bounds; operator failover alone does not establish operand lifecycle safety.
