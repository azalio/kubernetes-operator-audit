# Chapter 9 — Diving into FAQs and Future Trends
Source: PDF 244–264; printed 223–243. Entire chapter read. This is a recap, not an independent source of additional technical requirements.

## Essence
The FAQ connects terminology, architecture, implementation, packaging and lifecycle maintenance. Its audit value is intake/routing: identify what exists and which deeper checks apply. Repeated descriptions must not inflate finding counts or make SDK-specific implementation details universal.

## Routing checks
Book-derived topic map; the routing procedure and deduplication policy are explicit audit extrapolations.
## B09-01 — Identify controller and capability boundary
(pp. 224–226). Applies: all operator audits. Evidence: operand list, architecture, implementation language and documented features. Fail: auditor excludes a non-Go/non-SDK operator or assumes every operator promises Auto Pilot. Remedy: inventory actual behavior and route to B01-01 through B01-05; score claims against evidence, not toolkit labels.
## B09-02 — Identify API and access surface
(pp. 227–230). Applies: all operators; CRD checks only where CRDs exist. Evidence: resource kinds, schema versus CR examples, installation namespace, watch reach and access bindings. Fail: CR and CRD are confused or namespace scope is inferred from only one artifact. Remedy: route schema checks to B03-01 and scope/RBAC to B02-02 and B04-06, without duplicating findings.
## B09-03 — Trace executable control and reporting paths
(pp. 229–235). Applies: all controller implementations. Evidence: actual entrypoint, queue/reconcile equivalent, resource mutation, status, metrics and probes. Fail: audit checks only scaffolding or treats event history as authoritative current state. Remedy: route convergence to B03-02/B03-03 and B04-04/B04-05; diagnostics/HA to chapter 5. Language-equivalent code paths count.
## B09-04 — Select deployment/distribution route
(pp. 235–238). Applies: all installations, OLM checks conditionally. Evidence: supported deployment instructions and release artifacts. Fail: lack of OLM/OperatorHub is called a defect, or bundle publication is accepted as runtime proof. Remedy: apply chapter 6 to actual deployments and chapter 7 only to claimed bundle/catalog integrations.
## B09-05 — Separate release, API and storage versions
(pp. 239–242). Applies: evolving projects. Evidence: release metadata, served/storage API versions, conversion implementation and compatibility policy. Fail: one version number or a new CSV is assumed to prove all migration safety. Remedy: route to B08-01 through B08-07 and distinguish distribution upgrade paths from data/API conversion.

## Deduplication and traps
Record a defect once under its most specific underlying check; these IDs are coverage/routing gates, not extra severities for the same bug. The FAQ repeats simplifications: conditions are not boolean-only; cluster-scoped controllers still run namespaced Pods; ordinary CRDs are not necessarily Go-generated; framework pillars do not define eligibility. Its claim that the default Dockerfile copies assets conflicts with chapter 6's explicit added COPY instruction. Generic OLM downgrade assurances are not a supported rollback guarantee. Historical support windows and release cadence must be checked against current policy. Channels are catalog/distribution concepts, not simply arbitrary CSV fields. Use detailed chapters plus verified modern documentation when recap wording is imprecise.
