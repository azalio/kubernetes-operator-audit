# Chapter 4 — Implementation and generated assets

## Essence
Scaffolding connects API types, generated schemas/RBAC, resource templates, and a controller manager; compiling that skeleton is not proof of useful behavior. Reconciliation must distinguish absent primary resources from missing dependents, use the requested identity, maintain ownership, and watch relevant dependents. Generated output is part of the tested release, not an independent handwritten truth.

## Audit checks

## B04-01 — Reproducible generation
Applies: generated code/manifests. Evidence: tool versions, build targets, regeneration CI, committed artifacts. Fail: changing types/markers leaves stale deep-copy code, CRDs or RBAC in releases. Remedy: regenerate with declared toolchain and fail CI on unexpected diffs; do not fix generated output without fixing its source.
## B04-02 — Optional/default input behavior
Applies: configurable APIs. Evidence: omission, zero and invalid-input tests against installed schema and reconciliation. Fail: nil dereferences, invalid array indexing, or defaults disagree between API and workload. Remedy: explicitly model required/optional fields and defaults and validate before using values.
## B04-03 — Resource identity isolation
Applies: multi-instance or portable deployments. Evidence: name/namespace derivation and two-CR/two-namespace tests. Fail: hardcoded namespace/name, shared selectors, or a template writes into another instance's resources. Remedy: derive identity from the CR or documented policy and scope selectors/ownership correctly.
## B04-04 — NotFound versus operational failure
Applies: reconciliation API reads. Evidence: deleted-CR, missing-dependent, forbidden and transient-API-error tests. Fail: recreating deleted primary CRs, treating permission/network errors as absence, or swallowing errors needed for retry. Remedy: terminate normally for absent primary resources, create required absent dependents, propagate other failures with diagnostics.
## B04-05 — Ownership and watch coverage
Applies: managed dependent resources. Evidence: owner references, ownership setter error handling, watch registrations/mappings, delete/drift tests. Fail: orphaned resources, adoption of unrelated resources, or dependent changes never enqueue their owner. Remedy: establish valid ownership and map changes to the correct reconciliation key; use explicit mappings where ownership cannot apply.
## B04-06 — Permission generation matches behavior
Applies: SDK marker-based RBAC or equivalent manifests. Evidence: generated roles compared with actual API operations/status/finalizer paths. Fail: needed permissions missing, unused broad verbs retained without justification. Remedy: narrow scaffolding defaults and test with the shipped ServiceAccount, not developer cluster-admin credentials.
## B04-07 — Embedded resources are usable artifacts
Applies: embedded/template resource definitions. Evidence: decoding tests, packaged asset paths, type registration, rendered manifest validation. Fail: release binary lacks required files, bad decoding panics at runtime, or invalid templates only surface in production. Remedy: validate every embedded resource in the build and handle runtime errors appropriately. Go structs and YAML embedding are equally acceptable design choices.

## Applicability and cautions
Require a no-op fixed point rather than updates on every reconciliation. Check resource paths, object assignments, indexes and omitted/default inputs. Changing containerPort metadata does not itself change the process's listening configuration. Handle ownership setter errors and verify the deployed image identity. Owns maps ownership to the primary reconciliation key; matching names alone are insufficient. Require demonstrated upgrade behavior and verify generated layouts, tool versions and required-field semantics against the actual toolchain.
