# Chapter 10 — Case Study for Optional Operators – the Prometheus Operator
Source: PDF 266–294; printed 245–273. Entire chapter read.

## Essence
A real operator may predate the SDK, expose multiple related APIs, manage several operands with separate controllers, and construct resources directly in code. Prometheus illustrates how independent workload and monitoring configuration objects enable delegation, how selectors connect those objects, and how an operator translates the public API into concrete configuration and StatefulSets. Audit the entire translation and activation path rather than conformity to the nginx tutorial.

Checks derive from the book's case study; proposed tests and remedies are original audit synthesis. Prometheus-specific checks apply only to that integration; general configuration principles transfer to other operands.

## B10-01 — Multi-API responsibility and delegated configuration
Source: pp. 254–261. Applies: operators with multiple CR kinds or tenant configuration.
Evidence: API/controller map, RBAC delegation, relationships between workload and configuration objects.
Fail: unrelated configuration is accepted across tenant boundaries, or no controller owns a supported resource's effect.
Remedy: explicitly map kinds to controllers/operands and enforce intended namespace and selection boundaries. Cross-tenant negative tests are audit extrapolation.

## B10-02 — Monitoring selection chain
Source: pp. 257–261. Applies: Prometheus monitor integration.
Evidence: Prometheus monitor selectors, monitor labels, namespace selectors, Service/Pod selector labels, named endpoint ports, generated scrape jobs and live target results.
Fail: a valid-looking monitor selects no intended targets or unintended ones, or port/namespace mismatch prevents collection.
Remedy: verify each selection layer independently and demonstrate one complete scrape path. Do not confuse a ServiceMonitor's own labels with its selector for Services.

## B10-03 — Configuration generation and activation
Source: pp. 249–253, 261–264. Applies: file/flag-configured operands.
Evidence: CR-to-config translation, generated Secret/ConfigMap, mounts, command flags, reload sidecar or rollout mechanism and actual active configuration.
Fail: desired settings reach the API but not the running application, reload failures are silent, or all changes cause avoidable disruption.
Remedy: distinguish restart-required flags from reloadable settings, validate generated config, and observe successful activation. Last-known-good handling and invalid-config tests are audit extrapolation.

## B10-04 — Full dependency watch and safe state construction
Source: pp. 262–265. Applies: controllers with derived configurations/workloads.
Evidence: watches for primary and contributing resources, mapping to affected instances, DeepCopy usage, config/workload create-or-update logic.
Fail: modifying a Secret or selected configuration object does not reconcile, shared cache objects are mutated, or missing primary objects are retried as permanent errors.
Remedy: watch or otherwise refresh every relevant dependency, copy cached data before mutation, and distinguish NotFound from other API failures. Reuse B03-03 for fixed-point defects rather than duplicate findings.

## B10-05 — Separate controller and operand permissions/status
Source: pp. 262, 265, 270. Applies: separately authenticated operator and operand.
Evidence: both ServiceAccounts and bindings, operator diagnostics, per-instance workload status.
Fail: the controller's rights are assumed to authorize the operand, privileges are copied indiscriminately, or aggregate status masks a failed instance.
Remedy: grant each component its necessary operations and report actual workload-specific state. Conditions are useful but this case study demonstrates other meaningful status fields.

## B10-06 — Distribution and ongoing support fidelity
Source: pp. 266–272. Applies: multiple distribution paths or externally maintained operands.
Evidence: direct-install manifests versus OLM bundle, versions, dependency update review/tests, operator-specific support contacts.
Fail: a file named bundle.yaml is assumed to be an OLM bundle, shipped installation paths drift, or support ownership is ambiguous.
Remedy: validate each advertised installation artifact and retain explicit operator/operand support boundaries. Automated dependency PRs do not substitute for compatibility testing.

## Traps and extrapolation boundaries
The chapter first overstates that config changes require restarts, then explicitly explains runtime reload via the config-reloader sidecar: preserve that correction. It describes missing primary CR as an error while quoted code correctly returns nil on NotFound. CRD counts, fields, historical versions and status structure are snapshots, not current requirements. StatefulSets, multiple instances, native resource construction and non-SDK sync functions are valid designs. Ingress is not the only way to expose a Service. The example command flag spelling and obsolete StatefulSet API references require validation. 'Optional' means not intrinsically part of the Kubernetes control plane, not operationally unimportant; monitoring may be critical to the audited service.
